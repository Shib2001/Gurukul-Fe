# Gurukul Weekly Sprint Roadmap

## 1. Purpose

This document defines the recommended sprint plan for taking Gurukul from an
empty project to a production-ready first release.

The roadmap assumes three independent repositories:

```text
gurukul-frontend
gurukul-backend
gurukul-ai
```

The plan uses two-week sprint cycles internally, but each numbered phase is
written as a one-week execution plan. This gives the team a weekly target,
review point, and demonstrable outcome.

The first production release is intentionally focused:

- Secure student accounts
- Subject and teacher catalog
- Text-based AI tutoring
- Approved-content RAG
- Weekly quizzes
- Progress and leaderboard
- Basic voice learning
- Monitoring, security, and deployment

Advanced features such as full-duplex voice, payments, recommendations,
mobile applications, and institution management should follow after the first
stable release.

---

## 2. Delivery principles

### 2.1 Build a vertical slice early

Do not spend months building isolated infrastructure. By the end of Week 4,
the team should prove:

```text
Frontend -> Backend -> AI service -> OpenRouter -> Backend -> Frontend
```

### 2.2 Keep the first release narrow

The first release should support one complete learning loop:

```text
Register
  -> choose a teacher
  -> ask questions
  -> learn from responses
  -> complete a quiz
  -> view progress
  -> see weekly rank
```

### 2.3 Backend remains authoritative

The backend owns:

- Authentication
- Permissions
- Durable messages
- Quiz attempts
- Scores
- Progress
- Leaderboards

The AI service owns:

- LangGraph workflows
- Prompt policies
- RAG
- OpenRouter
- Voice provider orchestration

The frontend owns:

- Presentation
- Browser interaction
- Real-time rendering
- Local UI state

### 2.4 Every week ends with evidence

Each week must finish with:

- Working code or reviewed design output
- Tests for the completed scope
- Updated documentation
- A short demo
- Known issues recorded
- A decision about whether the next week can begin

---

## 3. Team and working model

The roadmap can be followed by one developer, but the workload is easier with
three workstreams:

```text
Frontend workstream
Backend workstream
AI/platform workstream
```

Shared responsibilities:

- Product decisions
- Security and privacy
- Contract changes
- Testing
- Deployment
- Documentation

### 3.1 Recommended weekly rhythm

```text
Monday:
  Sprint planning, clarify requirements, define acceptance criteria

Tuesday-Wednesday:
  Main implementation

Thursday:
  Integration, contract tests, and bug fixing

Friday:
  Demo, review, documentation, release decision, next-week planning
```

### 3.2 Weekly status categories

Use:

```text
Not started
In progress
Blocked
Ready for review
Done
Deferred
```

Do not mark a feature done merely because code exists. It is done only when
its acceptance criteria and tests pass.

## 4. Product scope for the first release

### Must have

- Student registration and login
- Student profile and onboarding
- Mathematics, Science, and English Literature teacher catalog
- Text chat with at least one production-quality teacher
- Conversation persistence
- OpenRouter integration through the AI service
- Curated RAG content
- Weekly quiz attempts
- Deterministic scoring
- Weekly leaderboard
- Progress summary
- Basic voice turn-based interaction
- Rate limits and token budgets
- Error handling and observability
- Production deployment and backups

### Should have

- All three teachers evaluated and enabled
- Voice transcription and text-to-speech
- Notifications
- Admin content publishing
- Quiz feedback generated by AI
- Accessibility and performance checks
- Data export and deletion workflow

### Defer

- Full-duplex voice
- Payments and subscriptions
- Institution tenancy
- Mobile apps
- Personalized recommendation engine
- Social groups
- Advanced gamification
- Arbitrary AI tools
- Open-ended web search
- Kubernetes unless operationally required

|---:|---|---|
| 1 | Product foundation | Decisions, scope, repositories, contracts |

## 6. Cross-repository dependency order

Use this order when work crosses repositories:

```text
1. Define or update contract
2. Update backend schemas and API
3. Update AI contract or implementation
4. Update frontend generated types
5. Integrate frontend behavior
6. Run contract and end-to-end tests
```

For a backward-compatible change:

```text
1. Backend accepts old and new shape
2. AI/frontend adopt new shape
3. Old shape is deprecated
4. Old shape is removed in a later version
```

Never deploy a frontend that requires an API field before the backend version
that provides it is available.

## 10. Risk register

| Risk | Impact | Mitigation |
|---|---|---|
| OpenRouter outage | Chat unavailable | Bounded fallback, safe retry, status messaging |
| Token cost spike | Budget overrun | Redis budgets, route limits, alerts, output caps |
| Prompt injection | Unsafe or leaked behavior | Isolation, filters, output validation, evaluation |
| Incorrect AI explanation | Learning harm | RAG, citations, evaluation, uncertainty policy |
| Database failure | Progress or score loss | Backups, PITR, restore testing |
| Redis outage | Limits and queues impaired | Fail-closed/restricted mode, durable PostgreSQL |
| WebSocket failure | Poor chat experience | REST recovery, reconnect, polling/SSE fallback |
| Voice provider failure | Voice unavailable | Text fallback and explicit status |
| Quiz scoring bug | Incorrect ranking | Deterministic tests, versioned scoring, audit |
| Unauthorized data access | Privacy/security incident | Object authorization, security tests, audits |
| Excessive scope | Schedule failure | Must/should/defer scope and release gates |
| Poor retrieval quality | Misleading answers | Approved content, retrieval evaluation, citations |

Review the risk register every Friday.
